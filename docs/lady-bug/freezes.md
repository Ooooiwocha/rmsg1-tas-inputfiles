# レイディバグ中の「止まって見える状態」の分類

バグ発火後、何を押しても進まないように見える状態を、裏で何が起きているかで分けたものです。
検出は `ladybug-tools.lua`／`freeze-detect.lua` で行えます。

調べ方：BizHawk 2.11.1（BSNESv115+）のステートから、プログラムの実行位置・呼び出し元・
作業用RAMの変化・全ボタンへの反応・3,000フレーム放置の結果を見ています。

## 1. 本当のフリーズ（どの操作でも抜けられない）

入力を読む処理に戻らないので、ボタンの組み合わせを試す意味がありません。

| 型 | 止まっている処理 | 終わらない条件 | 見分け方 |
|---|---|---|---|
| 窓の行送りループ | 窓に文字を書くとき、「行番号（$160F+Y）が窓の高さ（$1606+Y）以上なら1行送って行番号を1減らす」を繰り返す（$00:A45C〜、$00:C752〜） | 窓の高さが 0 | ループ本体 $00:A464／$00:C75A に来たとき $1606+Y が 0 |
| 選択肢の窓の送りループ | 選択位置（$12CC）が見えるところまで、下端の行番号（$1618+Y）を2ずつ増やして一覧を送る（$00:BD8F〜） | $12CC が $FF（または $FE で行番号が偶数） | ループ本体 $00:BD97 に来たときの $12CC |
| 割り込み停止中のフレーム待ち | 「次のフレームまで待つ」処理（$00:8936〜）。合図 $1206 に 1 を書き、割り込み処理が 0 に戻すのを待つ | 割り込みが止められたまま待ちに入った | 入力を読まないフレームが続く（ムービーでは最長37）。作業用RAMが一切変わらず、時計と重なる12枚目のメモも止まる |

| 暴走 | プログラムがRAMの中（$00:0000 付近など）を実行し、スタックの位置がメモリ全体を動き回ってRAMを壊し続ける | 確認した例の原因：オブジェクトを子ごと削除する処理（$02:84E2、データは $7F）が自分自身を呼び出す作りで、親子のつながりが輪になっていた（$7F:060F の子が $7F:20FF、その子が $7F:060F）ため呼び出しが終わらず、1回ごとに8バイトずつスタックが伸びてRAMを上書きした。つながりが輪になった理由は未特定 | フレームの切れ目の実行位置がRAMにある状態が続く（ムービーでは1回もない）。画面は真っ暗になり、入力を読まないフレームが続く |

補足：

- 選択肢の窓の送りループには、フレームを待たずに回る出方（1フレームに約460回）と、
  1行送るたびに画面更新を待つ出方（2フレームに1回）の両方がある。
- 命令 `14 n` は n×2 フレーム待つ。n が 0 のときは約65,000フレーム（約18分）待つので、
  実質フリーズに見えるはず（実例は未確認）。

## 2. 止まって見えるが、放置すれば進む状態

入力を読まずに時間だけが過ぎる状態です。この間はボタンを押しても何も変わりません
（ただし12枚目のメモは時計と一緒に進むので、経過フレーム数は後の行き先に効きます）。

| 状態 | 最後に読んだ命令 | 観測した再開までの時間 |
|---|---|---|
| フィールド側の処理の実行中 | `0F`、`06` | 76〜222フレーム |
| 窓の文字表示・行送りの途中 | `13` | 89〜114フレーム |
| 時間待ち | `14 n` | 83〜194フレーム |

## 3. 入力を待っている状態

| 状態 | 命令 | 効く操作 |
|---|---|---|
| Aボタン待ち | `12` | A（Xも効く場面がある） |
| 行き先を選ぶマップ画面 | `0D n` | カーソルで行き先を変える。カーソルのあとにA、またはBでマップが閉じて再開する。Aだけだと別のマップに切り替わる場合がある |

## サンプルでの割合

バグ発火後にA・Xを適当に押して進め、50フレーム何も起きなくなった状態58個の内訳：

| 分類 | 個数 |
|---|---|
| AかXで進む | 25 |
| マップ画面（入力待ち） | 12 |
| 放置すれば進む | 18 |
| 本当のフリーズ | 3 |

サンプルが小さく、A・Xだけで進めた範囲なので、割合は目安です。
