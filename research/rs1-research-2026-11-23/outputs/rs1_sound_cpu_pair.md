# ロマサガ1 レイディバグ　音のCPUが決め手になった組（反例の報告）

作成：2026-11-22

## 1. 要点

- 「音のCPUは決め手ではない」という結論は、7,259F の組では成り立つかもしれませんが、**一般には成り立ちません**。
- 別の組（下記）で同じようにセーブステートを領域ごとに入れ替えたところ、次の2つを**同時に**書き写したときだけ、行き先が入れ替わりました。
  - 音のCPUのメモリ（この組では 10,904 バイト違う）
  - セーブステート先頭側の16バイト（中身は未特定。音の処理の状態の一部と考えている）
- 本体のCPUの状態、WRAM、VRAM は、書き写さなくても行き先が入れ替わりました。
- 行き先が分かれる原因は少なくとも2種類あると考えるべきです。
  - 本体のCPUの進み具合のずれ（そちらの 7,259F の組）
  - 音のCPU側の状態の違い（こちらの組）

## 2. 調べた組

- 入力：TAS（7,279F版）の入力を 0〜7,197 行目まで再生し、そのあと無入力。指定したフレームに A を1フレームだけ押す。
- A: 12,002F に押す。B: 11,594F に押す。
- どちらも、12枚目のメモで読んだ最初のジャンプの行き先は **$1A:B469**。
- ジャンプ先を読んだフレームの頭（以下「T時点」）のセーブステートを比べた。

| | その後の読み方 |
|---|---|
| A | 150F目に $1B:9E83 を読む（ボタン待ち） |
| B | 151F目に $1B:9D83 を読む（ボタン待ち） |

T時点から148F目、効果音の命令 `0B 89`（$1B:A06E）の処理で、音のCPUの返事を待つ空回り（$04:xxxx の `CMP $2140 / BNE` のループ）が A は 211回、B は 3,029回でした。B はその分そのフレームの中で遅れ、次の文字の表示が1フレーム後ろにずれて、読む場所が256バイト変わります。

## 3. セーブステートの入れ替え

セーブステートは 416,881 バイト。領域の区切りはそちらの表に合わせました（こちらの環境でも長さは同じ）。

| 領域 | 範囲（バイト目） | A と B で違うバイト数 |
|---|---|---|
| 先頭側 | 0〜114,439 | 16 |
| VRAM | 114,440〜179,975 | 156 |
| CGRAM | 179,976〜180,487 | 0 |
| 本体のCPUなど | 180,488〜184,391 | 1 |
| WRAM | 184,392〜315,463 | 172 |
| 音のCPUのレジスタやタイマーと思われる部分 | 315,464〜315,907 | 8 |
| 音のCPUのメモリ | 315,908〜381,443 | 10,904 |
| その他 | 381,444〜 | 31 |

A の状態に、B の該当領域を書き写して流した結果：

| 書き写した領域 | 結果 |
|---|---|
| 全部 | B と同じになる |
| 全部から「先頭側」を除く | A のまま |
| 全部から「音のCPUのメモリ」を除く | A のまま |
| 全部から「本体のCPUなど」を除く | B と同じになる |
| 全部から「WRAM」を除く | B と同じになる |
| 全部から「VRAM」を除く | B と同じになる |
| 全部から「音のCPUのレジスタ…」を除く | B と同じになる |
| 全部から「その他」を除く | B と同じになる |
| 本体のCPUなど | A のまま |
| 本体のCPUなど＋WRAM | A のまま |
| 本体のCPUなど＋WRAM＋VRAM | A のまま |
| 音のCPUのメモリ | A のまま |
| 先頭側 | A のまま |
| 先頭側＋音のCPUのレジスタ… | A のまま |
| **先頭側＋音のCPUのメモリ** | **B と同じになる** |

「先頭側」で違っていた16バイト（バイト目：A の値 > B の値）：

```
101575:4C>00 101576:16>00 101581:00>01 101604:18>88 101605:6D>17 101606:05>34
101607:3C>22 101608:10>00 101704:11>0B 101706:1C>21 101711:11>0B 101713:24>2D
101714:06>0D 101718:01>0B 101719:01>00 101722:01>00
```

この部分が何の状態かは、まだ特定できていません。音のCPUのメモリと組で効くので、音の処理側（音のCPUの内部の状態や、本体との同期の状態など）の一部ではないかと考えています。そちらの表で「音のCPUのレジスタやタイマーと思われる部分」とされている 315,464〜315,907 は、この組では書き写さなくても結果が入れ替わりました。区切りの推定が合っているかも、確かめたほうがよいと思います。

## 4. 補足：$181C について

$181C は「処理の残り時間」ではありません。フィールドの処理（$01:817C〜817F）が毎フレーム 0→16 まで1ずつ増やし、16 の次に 0 に戻す、17フレーム周期のカウンタです（直接ページ $1800 のときの `$1C`）。隣の $181B は毎フレーム1ずつ増え続けるだけのフレームカウンタです。命令 `0F` の長さはこの周期のどこで読んだかで変わり、こちらで試した14組中10組は、$181C の1バイトを書き写すだけで行き先が入れ替わりました。


## 追記（訂正）：時計の値だけでも入れ替わる

- 「音のCPUのメモリと 101,604〜101,608 を一緒に書き写したときだけ入れ替わる」は誤りでした。A の状態に B の 101,604〜101,608 だけ（101,608 の1バイトだけでも）を書き写すと、音のCPUのメモリが A のままでも B の行き先になりました。
- 前の試しで「先頭側（0〜114,439）だけ」を書き写して入れ替わらなかったのは、時計と一緒に 101,704〜101,722 の8バイトも B の値になっていたためです。時計＋この8バイトでは A に戻り、そこへ音のCPUのメモリも加えると B になりました。
- まとめると、決め手は音のCPUの時計（本体とのずれ）です。ただし、どの値で遅れるかの区間の位置は、音のCPUのメモリや 101,704〜101,722 の値（音のCPUのタイマーなどと推定）で変わります。
