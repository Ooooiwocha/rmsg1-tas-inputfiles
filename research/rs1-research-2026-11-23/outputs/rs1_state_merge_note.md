# ロマサガ1 レイディバグ　探索で「同じ状態」をどう判定するか（共有メモ）

作成：2026-11-22

## 1. 結論

- 行き先は、ゲームのRAM（WRAM）だけでは決まりません。WRAMが同じでも、次の違いがあれば、その先で別の行き先になることを確かめました。
  - 音のCPUのメモリと、音のCPUの時計の位置（本体のCPUとのずれ）
  - フレームの切れ目で、本体のCPUがどこまで処理を進めていたか（そちらで調べた 7,259F の組）
- そのため、探索で「同じ状態に着いたら1つにまとめる」ときに、WRAM（またはWRAMの一部のバイト）だけで判定すると、別の結果になる状態を捨てることがあります。その場合、「見つからなかった」は**その探索の範囲では見つからなかった**という意味にとどまり、厳密な証明にはなりません。
- 厳密にするには、**エミュレーターの状態全体（セーブステート全体）が一致したときだけ**まとめる必要があります。エミュレーターは、状態全体が同じなら同じ入力に対して必ず同じ動きをするので、何も捨てずに済みます。

## 2. 根拠：音のCPU側の状態が決め手になった組

詳しくは別紙「rs1_sound_cpu_pair.md」。要点だけ書きます。

- TAS（7,279F版）の入力を 0〜7,197 行目まで再生し、そのあと無入力。A を 12,002F に押すか、11,594F に押すかの2通り。
- どちらも、12枚目のメモで読んだ最初のジャンプの行き先は $1A:B469。
- その後、効果音の命令 `0B 89` の返事待ちの長さが違い（空回り 211回／3,029回）、150F目に $1B:9E83 を読むか、151F目に $1B:9D83 を読むかに分かれる。
- ジャンプ先を読んだフレームの頭のセーブステートを、領域ごとに片方へ書き写して試した結果：
  - WRAM・VRAM・本体のCPUの状態を全部書き写しても、行き先は入れ替わらない。
  - **音のCPUのメモリ**と、**セーブステートの 101,604〜101,608 バイト目（5バイト）**を一緒に書き写すと入れ替わる。どちらか片方だけでは入れ替わらない。

## 3. 101,604 バイト目からの値（音のCPUの時計と推定）

- 101,604 バイト目から始まる8バイトが1つの64ビットの数で、上位3バイトはいつも0。毎フレーム、5億〜3,500億くらいの範囲で行き来する（増え続けない）。下の位はいつも8の倍数。
- エミュレーターの bsnes は、本体のCPUと音のCPUを交互に少しずつ動かすために、それぞれが今どこまで進んだかを細かい単位の時計で持っています。この値は、その音のCPU側の時計（本体とのずれ）だと推定しています。目盛りの大きさ（1が何秒か）は未確認です。
- この値だけを書き換えて、遅れる（B）か遅れないか（A）を調べた結果（音のCPUのメモリは A のまま）：

| 時計の値 | 結果 |
|---|---|
| 0〜20億（5,000万刻み、41点） | すべて B |
| 1,300億〜1,435億 | すべて A |
| 1,457.5億〜2,042.5億（約22.5億刻みで27点連続） | すべて B |
| 2,065億〜2,200億 | すべて A |
| 2,200億〜3,900億（100億刻み） | すべて A |
| 4,000億 | B |

- 遅れるかどうかはランダムではなく、時計の値の**連続した区間ごと**に決まっていました。音のCPUが繰り返している処理の中に「この時間帯に合図が来ると、返事が次の回りまで待たされる」区間がある、という形です。
- 音のCPUのメモリを B のものに入れ替えると、遅れる区間の位置が変わりました（0付近と3,700億以上）。何を鳴らしているか、音の処理がどこまで進んでいるかで、繰り返しの中身や長さが変わるためだと考えられます。

## 4. 探索のまとめ方への影響

- WRAMの一部のバイトで状態をまとめる探索：上の2種類の違い（音のCPU側、本体のCPUの進み具合）を見落とすので、別の結果になる状態をまとめてしまうことがあります。結果は「この範囲では見つからなかった」と書くのが正確です。
- セーブステート全体で状態をまとめる探索：見落としはありません。ただし、セーブステートには実行のたびに変わるだけで動きに関係しない値（エミュレーター内部のポインタなど）が含まれるので、それを除いてから比べる必要があります。まとまる状態が減るぶん、時間はかかります。
- どちらの方式でも、言えるのは「このエミュレーター（BizHawk 2.11.1 の bsnes コア、この設定）の中では」までです。音のCPUの時計のずれのような部分は、実機の発振器の誤差やエミュレーターの作りで変わります。

## 5. TAS（7,279F）への影響

- TAS の経路で音のCPUの返事待ちが起きるのは、バグの最初のフレーム（7,195F）の1か所だけです。
- そのフレームで、返事待ちはフレームの約16%。スクリプトを最後に読むのはフレームの46%の位置で、54%の余裕があります。
- 約3,400通りの押し方で見た返事待ちの最長（空回り3,029回、TASの約3倍）まで延びても、増えるのはフレームの約33%分で、余裕に収まります。TAS の結果がこれで変わる心配は小さいです。

## 6. 同じジャンプ先から行き先が分かれる原因（確かめ済みのもの）

| 原因 | 値 | 効き方 | 確かめ方 |
|---|---|---|---|
| 文字を一気に出すフラグ | $1686 | `11` などが速く終わる | 書き換え |
| ウィンドウの行と横の位置 | $162F・$1627 | 行の繰り上げで `11` が1行3フレーム延びる | 書き換え |
| 今のウィンドウ | $128C（とスタックに退避したY） | `11` の処理が変わる | 書き換え |
| 17フレーム周期のカウンタ | $181C | `0F` の待つ長さ。14組中10組の行き先を決めていた | 書き換え |
| 命令 `3E` で反転するフラグ | $1290 | `13` が146フレームか98フレームか（行の繰り上げごとに画面へ送るか） | 書き換え |
| 読み込んである地図の画像 | $15E4 | `08` が29フレームか75フレームか | 書き換え |
| 11枚目のメモ | $12ED | `1A` で戻ったときの読む場所 | 書き換え |
| 音のCPUのメモリと時計 | WRAMの外 | 効果音の返事待ちで1フレームずれる | セーブステートの書き換え |
| 本体のCPUの進み具合 | WRAMの外（PC・S など） | そちらの 7,259F の組 | そちらで確認 |

補足：$181C は「処理の残り時間」ではありません。フィールドの処理（$01:817C〜817F）が毎フレーム 0→16 まで増やし、16 の次に 0 に戻す17フレーム周期のカウンタです。隣の $181B は、毎フレーム1ずつ増えるだけのフレームカウンタです。


## 追記（訂正）：時計の値だけでも入れ替わる

- 「音のCPUのメモリと 101,604〜101,608 を一緒に書き写したときだけ入れ替わる」は誤りでした。A の状態に B の 101,604〜101,608 だけ（101,608 の1バイトだけでも）を書き写すと、音のCPUのメモリが A のままでも B の行き先になりました。
- 前の試しで「先頭側（0〜114,439）だけ」を書き写して入れ替わらなかったのは、時計と一緒に 101,704〜101,722 の8バイトも B の値になっていたためです。時計＋この8バイトでは A に戻り、そこへ音のCPUのメモリも加えると B になりました。
- まとめると、決め手は音のCPUの時計（本体とのずれ）です。ただし、どの値で遅れるかの区間の位置は、音のCPUのメモリや 101,704〜101,722 の値（音のCPUのタイマーなどと推定）で変わります。
